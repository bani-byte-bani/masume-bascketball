# マス目バスケ 設計図書

ミニバスチームのお楽しみ会で遊ぶ、バスケットボール × チェス風ボードゲームのWeb実装。
現物のコートで遊ぶための「ルール検証用シミュレーター」であり、同時に単体でも遊べるゲーム。

- 実体： `masume-basket-game.html` （単一HTMLファイル。外部依存ゼロ）
- 動作環境： スマートフォンのブラウザを主対象（縦持ち、幅520pxまで）
- 用途： ①ルールのバランス検証 ②当日の説明用デモ ③そのまま遊ぶ

---

## 1. 設計上の大原則

この3つは、機能追加のときも壊してはいけない。

1. **単一HTMLファイルを維持する。** ビルド不要、npm不要、外部CDN不要。
   GitHub Pagesに置くだけで動くこと。依頼者はコードを書かず、生成されたファイルを
   アップロードする運用をしているため、ファイルが分かれると運用が破綻する。
2. **`localStorage` / `sessionStorage` を使わない。** 状態はすべてJS変数（`S`）で保持する。
3. **小学生が見て分かること。** UIの文言はひらがな多め、専門用語を避ける。
   低学年から高学年まで混在する場を想定している。

## 2. ゲームルール仕様

### 2.1 コート

| モード | 列(COLS) | 行(ROWS) | 実寸(1マス1.5m) |
|---|---|---|---|
| 3on3（既定） | 5 | 5 | 7.5m × 7.5m |
| 5on5 | 7 | 5 | 10.5m × 7.5m |

- 座標系は **`r`（行）= 1が手前、ROWSがゴール側**。`c`（列）= 1が左。
- ゴールは `r = ROWS + 1` の中央列の外側にある仮想点（`goalPos()`）。
- 両チームとも **同じゴールを攻める**（ハーフコート）。攻守交代しても盤の向きは変わらない。

### 2.2 シュートエリアと得点

- シュートエリア(SA) = 中央3列 × ゴール側3行。
  - 3on3: `SA_C=[2,4]`, `SA_R=[3,5]`
  - 5on5: `SA_C=[3,5]`, `SA_R=[3,5]`
- **2点**： SA内 かつ `r >= 4`（ゴールに近い2行）
- **3点**： 上記以外のすべてのマス（SA内の手前1行も、SA外も、コート内ならどこでも）

### 2.3 初期配置

ゴールは常に上（r=ROWS側）。攻撃側・守備側の「役割」で配置が決まる（`formations()`）。

**3on3** — 1列おきに縦のマッチアップを3組つくる。
```
        === ゴール ===
r5    ・    ・    ・    ・    ・
r4    ・    ・    ・    ・    ・
r3    ・    ・    ・    ・    ・
r2   青1    ・   青2    ・   青3
r1   赤1    ・   赤2    ・   赤3
```

**5on5** — 中央の背番号3がトップでボールを持ち、残りが左右に開く。
```
              === ゴール ===
r5   ・    ・    ・    ・    ・    ・    ・
r4   ・    ・    ・    ・    ・    ・    ・
r3  青1    ・   青2    ・   青4    ・   青5
r2  赤1    ・   赤2   青3   赤4    ・   赤5
r1   ・    ・    ・   赤3    ・    ・    ・
```

ボールは `Math.ceil(N/2)` 番（3on3なら2番、5on5なら3番）が持って開始する。

### 2.4 手番の流れ

背番号順に、攻撃側 → 守備側 を交互に繰り返す。

```
[ATK] 攻撃側の S.num 番が移動
   ↓
[ACTION] パス / シュート / なにもしない を選ぶ
   ↓
[DEF] 守備側の S.num 番が移動
   ↓
S.num を +1（Nを超えたら1に戻る）→ [ATK] へ
```

### 2.5 移動

- 8方向（タテ・ヨコ・ナナメ）。
- **歩数モード**（`STEP2`）で切り替わる：
  - `false`（既定）: 全員1歩
  - `true`: ボールを持っていない人は **2歩まで**（1歩で止まってもよい）。ボール保持者は1歩。
- 人がいるマスは **通り抜けも着地も不可**。
- 「その場にとどまる」も選択可（手数は消費する）。
- 動けるマスが1つもない場合は自動でその番をスキップする。

### 2.6 パス

- **パスを出せる相手は「この手番で動いた選手」ただ1人だけ。** 動いていない選手には出せない。
- 経路はタテ・ヨコ・ナナメの直線のみ。距離は無制限。
- 直線上に **相手チームの駒が1つでもあれば通せない**（味方は妨げにならない）。
- 動いた本人がボールを持っている場合、パス先は存在しない（＝パス不可）。

### 2.7 シュート

**打てる条件（`canShoot()`）**： ボール保持者 == この手番で動いた選手。

この1つの式で、以下すべてを正しく判定できる：
- 自分でドリブルして動いた → 打てる
- 誰かからパスを受け取った → 打てる
- 他人が動き、自分はボールを持ったまま静止 → 打てない
- リバウンドを取った直後 → 打てる（取った選手に `S.num` と `S.ball` を合わせている）

**ブロック判定（`adjDefenders()`）**：
ボール保持者より **1行ゴール側の3マス**（`r+1`, `|dc| <= 1`）にいる守備だけが対象。
真横・後ろの守備は数えない。

- 対象0人 → そのまま成功判定へ
- 対象n人 → **1人ずつ順にジャンケン（各1/2）。全員に勝てば**成功判定へ。
  1人でも負けたらブロック成立 → 相手ボール。

**成功判定（サイコロ1〜6）**：

| 種別 | 成功条件 | 確率 |
|---|---|---|
| 2点シュート | 出目が3以下 | 1/2 |
| 3点シュート | 出目が6 | 1/6 |

### 2.8 リバウンド

シュートが外れたら、ゴールに一番近い攻撃側1人 対 守備側1人でジャンケン（1/2）。

- **攻撃側の勝ち**： ゴールに最も近い攻撃側の駒がボールを取得。手数リセット、
  その選手の手番として **すぐシュート／パスを選べる状態**（ACTIONフェーズ）で再開。
- **守備側の勝ち**： 攻守交代。

### 2.9 ショットクロック

- 攻撃側の移動回数が `SHOT_CLOCK = N × 3`（背番号3周ぶん）に達しても
  シュートしなければ、相手ボール。
- 3on3なら9手、5on5なら15手。

### 2.10 攻守交代と試合終了

**交代する条件**
1. シュートが決まった
2. シュートのジャンケンに負けた（ブロック）
3. リバウンドのジャンケンに負けた
4. ショットクロック超過

交代時は **全員が初期配置に戻る**。

**試合終了**： `TOTAL_ATTACKS = 6`（赤3回・青3回）を消化した時点。得点の多い方が勝ち。

## 3. 実装構造

### 3.1 状態オブジェクト `S`

すべてのゲーム状態はこの1つのオブジェクトに集約する。

```js
S = {
  pieces: [{ id:'A1', team:'A', num:1, r:1, c:1 }, ...],  // 全駒
  atk: 'A',            // 現在の攻撃チーム（'A'=赤 / 'B'=青）
  ball: 'A2',          // ボール保持者の id
  num: 1,              // 現在の背番号（手番）
  moves: 0,            // この攻撃での攻撃側移動回数（ショットクロック用）
  phase: 'ATK',        // 'ATK' | 'ACTION' | 'DEF'
  sel: null,           // 'PASS' 選択中かどうか
  scoreA: 0, scoreB: 0,
  attackNo: 1,         // 何回目の攻撃か（1〜6）
  gameOver: false,
  log: [],             // 画面下のログ
}
```

### 3.2 主要関数

| 関数 | 役割 |
|---|---|
| `setMode(n)` | 3on3 / 5on5 の切替。COLS・SA_C・SHOT_CLOCKを更新 |
| `formations()` | モードごとの初期配置を返す |
| `initState(atk)` | 新しい攻撃の初期状態を生成 |
| `newPossession(atk, reason)` | 攻守交代。6回消化していれば `endGame()` |
| `legalMoves(p)` | 移動可能マスをBFSで列挙（`d`に何歩目かを持つ） |
| `passTargets()` | パス可能な相手（0人か1人） |
| `clearLine(a,b)` | 直線かつ相手に遮られていないか |
| `canShoot()` | シュート可否 |
| `adjDefenders(p)` | ブロック対象の守備（ゴール側3マス） |
| `doShoot()` → `janChain()` → `resolveShot()` | シュート処理の連鎖 |
| `missShot()` | リバウンド処理 |
| `ensureMovable()` | 詰み・選択肢なしの自動スキップ |
| `render()` | 画面全体の再描画（状態→DOM） |
| `cpuMove()` / `cpuAction()` | CPU（青）の思考 |

### 3.3 描画の考え方

`render()` が `S` を読んで **画面全体を作り直す**（差分更新はしない）。
状態を変えたら `render()` を呼ぶ、という一方向の流れを守る。

### 3.4 CPU（青チーム）の思考

既定でON（`cpuBlue = true`）。0.55秒の遅延を入れて「考えている」風に見せる。

**移動の評価（`defCellScore`）— 基本方針はマークよりゴール側に立つこと**
- ターゲット（近ければボール保持者、遠ければ自分と同じ背番号の相手）を決める
- ちょうど正面（ゴール側3マス） → +6
- 正面でなくてもゴール側 → +2
- ターゲットより手前（ゴールから遠い側） → −2
- 距離が近いほど加点、同条件ならゴールに近い方をわずかに優先

**攻撃の評価（`atkCellScore`）**
- ゴールに近いほど加点、シュートエリア内なら大きく加点、守備が隣接していれば減点

**行動の判断（`cpuAction`）**
- まだ打てない → 動いた選手にパスできれば必ず出す。出せなければ「なにもしない」
- **1周目（`S.moves <= N`）はシュートしない**（突撃→即シュートの単調さを避けるため）
- 2周目以降 → シュートを狙う

## 5. 変更時の注意（過去に踏んだ罠）

- **`confirm()` / `alert()` を使わない。** サンドボックス環境ではブロックされ、
  ボタンが無反応になる。確認が必要なら自前のモーダルを使う。
- **極小サイズの装飾はディテールを削る。** ボールの柄は当初4本線（縦・横・左右のシーム）で
  実装したが、24〜28pxでは全部潰れて地球儀に見えた。十字2本に簡略化した経緯がある。
- **設定ボタンは「切り替え先」でなく「現在値」を見せる。** ラジオボタン形式にして
  選択肢を常時表示する。
- **フェーズ遷移のたびに `S.sel = null`。** パス選択状態が守備の手番に持ち越されると誤動作する。
- **バランス調整は必ず数値で確認する。** 感覚で変えると崩れる。→ 第6章

## 6. バランス調整の指針

過去のシミュレーション結果（3on3、9手、CPU同士）：

| 設定 | シュート到達 | ノーマーク率 | 1攻撃の期待得点 |
|---|---|---|---|
| 現状（どこからでも3点／ブロックはゴール側のみ） | 71% | 100% | 0.55 |
| ブロック範囲をとなり8マスに拡大 | 50% | 100% | 0.31 |
| シュートをエリア内限定＋ブロックはゴール側＋真横 | 51% | 52% | 0.39 |
| シュートをエリア内限定＋ブロックはとなり8マス | 50% | 27% | 0.26 |

**重要な知見**： 「どこからでもシュートできる」限り、守備が3人ではコートを守りきれず、
攻撃側は必ず空きマスを見つけられる。→ **ブロック範囲だけを広げても競り合いは生まれない。**
競り合いを増やしたいなら、シュート可能範囲の制限とセットで考えること。

調整案を検討するときは、盤面をNode.jsで再現して数千回試行し、
「シュート到達率」「ノーマーク率」「1攻撃あたり期待得点」を比較してから決める。
